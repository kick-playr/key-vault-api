# APP-35 local vault design

Storage revision (user requested MongoDB): the MongoDB design in `../plans/2026-11-01-mongodb-storage.md` supersedes the original file-backend choices below. Current code uses encrypted per-namespace MongoDB documents with atomic revision-based replacement, database-backed reads, and no file lock. ## Intent and decisions

Provide a local development vault that automatically creates and names a tenant's required keys, persists supplied secrets, and loads validated runtime snapshots without copying values into dotenv files. The user selected NestJS/TypeScript and Azure Key Vault as the compatibility target, and instructed continued implementation. Remaining choices below are implementation defaults, not claims of external architecture/security approval.

The repository is empty. There are no existing consumer mappings, initialization hooks, or migration sources to integrate. Deliver a standalone NestJS server, reusable server-only runtime client, example manifest, and integration instructions. Do not invent existing consumers or generate live credentials.

## Approach

Use one NestJS process with a transactional encrypted local file. This keeps bootstrap small and avoids a separate database. An external Azure vault would defeat offline development; a plaintext emulator would violate persistence requirements. One process exclusively owns the store through a lifetime lock; competing processes fail closed. In-process mutations serialize, write a complete encrypted file through an atomic rename, and publish memory only after persistence succeeds.

## Supported contract

Pin data-plane requests to `api-version=2025-07-01`. Implement a documented subset based on Microsoft's REST reference: key create/get/list versions/update attributes/delete; secret set/get/list versions/update attributes/delete; RSA-OAEP-256 encrypt/decrypt on explicit key versions. Azure create/set creates a new version; manifest reconciliation is a separate local extension and reuses valid existing versions. Responses use Azure bundle, attributes, base64url, key ID and error shapes. Unsupported fields, algorithms, API versions and operations fail explicitly. No Entra ID emulation, certificates, HSM, import/export, backup, soft-delete/recovery, purge, or full SDK compatibility claim. Deletion is permanent locally and is documented as a compatibility deviation.

Only RSA 2048/3072 keys with encrypt/decrypt operations; return public JWKs, never private fields. Private keys remain inside the encrypted store and crypto service. Secrets are strings with attributes, content type, tags, and immutable versions; metadata updates may disable a version. Disabled, expired, future-dated or deleted values cannot be read/used.

## Bootstrap, isolation and persistence

Bind to 127.0.0.1 only. Configure a 32-byte base64 master encryption key, store path, canonical loopback base URL, and JSON caller grants outside the vault. Tokens are high entropy bearer credentials with exact environment/tenant grants and read/write/crypto permissions. No unauthenticated data or provisioning endpoints; no wildcard namespaces. A caller selects its namespace via `x-vault-environment` and `x-vault-tenant`; authorization precedes lookup. Azure-compatible paths are relative to this locally selected vault namespace. IDs include namespace path segments so references are unambiguous; this local routing is an explicit deviation.

AES-256-GCM with fresh random nonce encrypts the entire store, including audit metadata and private JWKs. Directory mode 0700, files 0600, atomic rename, exclusive store lock. Reject symlink paths and insecure existing directory/file permissions. Wrong master key, corruption and lock conflict stop startup. Bootstrap configuration is validated without echoing values. Never log request bodies, headers, crypto values, secret values or arbitrary exception messages. Use safe error codes, no stack traces in HTTP responses. No CORS or frontend output; secret responses are restricted to authorized server callers and marked no-store. Local OS users with access to the master key and store can decrypt it: this is not an HSM or production service.

## Manifest and reconciliation

Schema version 1 contains entries with unique purpose, kind, scope (`tenant` or `process`), environment mapping and key options. Process-scoped entries are allowed only in the reserved `_shared` tenant namespace; tenant entries cannot be reconciled there. Use a deterministic `kv-<sha256(environment,tenant,purpose,kind)>` name (hex digest, provider-compatible length, no raw identifiers). Key mappings expose versioned key IDs only. Secret mappings expose values only in runtime snapshots.

Authenticated `POST /local/reconcile` accepts a positive monotonic revision, manifest, and optional supplied secrets keyed by purpose. The transaction creates only missing keys/secrets, reuses valid matching key parameters/usages, and rejects missing external secrets or mismatches atomically. Ordinary startup never rotates. Repeated same-revision requests must match the manifest and supplied-secret digest; different payloads at the same revision conflict. Older revisions conflict. Only newly supplied changed secret values create versions on a newer revision. A persisted revision high-water mark survives other mutations. Explicit Azure key create/secret set rotates; old versions remain addressable until disabled/deleted. Reconciliation after revocation fails rather than silently regenerating revoked material.

## Runtime contract

`RuntimeVault` fetches authenticated complete snapshots via `POST /local/snapshot` using the manifest. Call `initialize` before dependent clients are constructed; failures prevent readiness. A snapshot contains immutable mappings, manifest fingerprint, monotonic namespace generation, and expiry; it never contains private key material. Every store mutation increments generation. Refresh requires a monotonically increasing revision; lower generation responses cannot replace newer snapshots. Serialize refresh per namespace; publish only after all entries validate. Same revision retry is allowed, rollback is rejected.

Tenant snapshots are keyed by environment plus tenant; no tenant method touches process.env. Explicit process-only initialization permits approved mappings from `_shared`, rejects public/frontend/unsafe environment names, refuses conflicting existing variables, validates the whole set before writing and never refreshes process.env silently. Clients consuming process variables must restart for rotation; consumers using tenant snapshots recreate dependent clients after explicit refresh.

Fail closed on refresh failures: invalidate that namespace immediately; no last-known-good use after a failed refresh. Cache maximum age defaults to 30 seconds; expired snapshots fail. Retry is explicit by caller with the same revision; no unbounded automatic retry. An authenticated tenant configuration event calls reconcile then refresh; existing callers must wire this into their lifecycle. Revocation becomes effective on a refresh or expiry (at most TTL); crypto operations check current revocation immediately. No push invalidation or claim of instantaneous distributed revocation.
